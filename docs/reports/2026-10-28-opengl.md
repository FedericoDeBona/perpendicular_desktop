# OpenGL con Secure Boot attivo — 28 ottobre 2026

## Esito e perimetro

Indagine autorizzata dopo la segnalazione delle app senza OpenGL. Il driver kernel ufficiale ARM64 v0.4 rimane invariato; Secure Boot/Code Integrity attivi e TESTSIGNING disattivato sono requisiti inderogabili. Nessuna nuova accelerazione OpenGL implementata o distribuita. La diagnosi nella main è circoscritta ai prerequisiti; nessuna nuova prova clone o scena Creality.

**Scelta tecnica:** investigare OpenGL → Mesa Zink → Vulkan/Venus → GPU Mac, conservando il KMD firmato. Non è una candidata già funzionante. Primo gate prima di integrare Zink: esporre una GPU Vulkan reale con il driver corrente in un runtime host isolato, verificando prima supporto Venus e memoria condivisibile. Se ciò richiedesse un KMD diverso non firmato Microsoft, la candidata sarebbe respinta. Il codice v0.4 contiene già gestione esplicita di contesti Venus: questo giustifica l'esperimento, non ne dimostra la compatibilità completa.

## Misure nella main

- `graphics_info` iniziale: Red Hat VirtIO GPU 3D, hardwareDevice=true, softwareAdapter=false, featureLevel=45056 (11_0). Quattro adattatori presenti sani: una 3D e tre DOD.
- SecureBoot\State\UEFISecureBootEnabled=1. SystemStartOptions non contiene TESTSIGNING. Non è stata modificata alcuna protezione.
- SYS dal DriverStore: SHA256 `cfbc713754c7f0dcae4803017af3a0ebfc781d37fd57604f8ee8f2cfdad306c4`; Vulkan ICD `d4a5f7d6b28b6f1d3faaf70ccbc5cda42bc3340d9d8bd0f89f4e7202e824fd13`. Entrambi corrispondono ai pin del repository.
- Registro adattatori: OpenGLDriverName/OpenGLDriverNameWow assenti; VulkanDriverName punta al manifest ufficiale. L'assenza della chiave globale Khronos non dimostra assenza dell'ICD: il loader trova quello PnP.
- Probe con finestra nascosta sacrificabile: WGL context failed in ARM64 e x86. Non misura una versione OpenGL esposta a Creality x64 e non attribuisce da solo il fallimento all'ICD.
- D3D12CreateDevice FL11_0: `0x887A0004` in ARM64/x86; log Neptune esplicito: host senza supporto D3D12, caps `0x000000b6`.
- Loader Vulkan 1.3.301: ARM64 vkCreateInstance=-1, x86=-9. Diagnostica ARM64 individua `Failed to open dynamic library "vulkan_virtio.dll" with error 87`.
- Stessa DLL ufficiale caricata tramite percorso completo: LoadLibrary riuscita. Chiamate dirette all'ICD per separare caricamento ed enumerazione: creazione istanza riuscita, enumerazione riuscita ma **zero GPU**. La ripetizione con VN_DEBUG=init non aggiunge una diagnosi. È un controllo diretto circoscritto, non una correzione del loader né una qualifica Vulkan applicativa.
- QEMU corrente: virtio-ramfb-gl con neptune=on, blob=on, hostmem=512M; nessun venus=on. Manifest runtime `fcab7463…`: backend libdxmt-native, nessuna libreria Vulkan/MoltenVK elencata. Quindi abilitare il solo OpenGL guest non completa il percorso host.

## Confronto delle possibilità

| Percorso | Esito nella combinazione attuale |
| --- | --- |
| OpenGL su D3D12 / Compatibility Pack | Prerequisito hardware D3D12 assente; non installato alla cieca. |
| OpenGL su Vulkan / Zink | Candidata scelta per il prossimo gate; prima servono GPU Vulkan enumerabile, funzioni richieste da Zink e gestione della presentazione Windows. |
| ANGLE su D3D11 | Offre OpenGL ES; non equivale al supporto desktop OpenGL richiesto da programmi arbitrari. |
| Mesa software | Possibile percorso CPU, non soddisfa l'obiettivo di accelerazione GPU; non distribuito. |
| Nuovo driver kernel locale | Escluso se richiede test signing o riduzione delle protezioni. |

Non abbiamo importato driver Parallels né avviato REA: le fonti e le misure disponibili rispondono già alla domanda sul primo confine da correggere. Un'analisi Parallels avrebbe senso solo per una futura domanda precisa sulla presentazione/interop rimasta irrisolta.
