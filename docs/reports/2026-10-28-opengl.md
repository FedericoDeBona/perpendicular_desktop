# OpenGL con Secure Boot attivo — 28 ottobre 2026

## Esito e perimetro

Indagine autorizzata dopo la segnalazione delle app senza OpenGL. Il driver kernel ufficiale ARM64 v0.4 rimane invariato; Secure Boot/Code Integrity attivi e TESTSIGNING disattivato sono requisiti inderogabili. Nessuna nuova accelerazione OpenGL implementata o distribuita. La diagnosi nella main è circoscritta ai prerequisiti; nessuna nuova prova clone o scena Creality.

**Scelta tecnica:** investigare OpenGL → Mesa Zink → Vulkan/Venus → GPU Mac, conservando il KMD firmato. Non è una candidata già funzionante. Primo gate prima di integrare Zink: esporre una GPU Vulkan reale con il driver corrente in un runtime host isolato, verificando prima supporto Venus e memoria condivisibile. Se ciò richiedesse un KMD diverso non firmato Microsoft, la candidata sarebbe respinta. Il codice v0.4 contiene già gestione esplicita di contesti Venus: questo giustifica l'esperimento, non ne dimostra la compatibilità completa.

## Confronto delle possibilità

| Percorso | Esito nella combinazione attuale |
| --- | --- |
| OpenGL su D3D12 / Compatibility Pack | Prerequisito hardware D3D12 assente; non installato alla cieca. |
| OpenGL su Vulkan / Zink | Candidata scelta per il prossimo gate; prima servono GPU Vulkan enumerabile, funzioni richieste da Zink e gestione della presentazione Windows. |
| ANGLE su D3D11 | Offre OpenGL ES; non equivale al supporto desktop OpenGL richiesto da programmi arbitrari. |
| Mesa software | Possibile percorso CPU, non soddisfa l'obiettivo di accelerazione GPU; non distribuito. |
| Nuovo driver kernel locale | Escluso se richiede test signing o riduzione delle protezioni. |

Non abbiamo importato driver Parallels né avviato REA: le fonti e le misure disponibili rispondono già alla domanda sul primo confine da correggere. Un'analisi Parallels avrebbe senso solo per una futura domanda precisa sulla presentazione/interop rimasta irrisolta.

## Seguito autorizzato: candidata host e primo clone

L'utente riavvia Windows e autorizza gli interventi necessari. Main iniziale74247 collegata/readiness positiva. Preparata una candidata privata da una copia dei sorgenti Wire2 conservati, con `venus=true`, `neptune=true`, render server/worker a processi, senza modificare la base di riferimento. MoltenVK ufficiale1.4.2, archivio macOS SHA256 `f95765a6229cb7b915990a2890ce12ebe36a730b021545d3d52ae69ce4c4024e`. Output fuori Git in `QA/opengl-venus-20261028`.

**Gate host superati:** il probe nativo enumera AppleM4 integrata, Vulkan1.1.357, `VK_EXT_external_memory_host`, `VK_EXT_external_memory_metal`, timeline semaphore. La prima richiesta della sola estensione loader portability_enumeration fallisce-7 sul caricamento diretto MoltenVK: il probe finale enumera prima le estensioni e la richiede soltanto se disponibile. Inizializzazione virgl e creazione/distruzione di un contesto Venus native riuscite. Non sono una prova di rendering Vulkan nel guest.

**Clone circoscritto:** nuovo UUID444cf545, overlay su checkpoint offline completo26ottobre (nessun backing nella main accesa), EFI/TPM privati, rete `restrict=on` e solo guestfwd del bridge su porta locale separata. Nessuna cartella Mac condivisa. L'UUID Windows letto via CIM concorda con QMP; il listener è dedicato al clone. Protezioni SecureBoot1 e boot options senza TESTSIGNING; SYS/ICD con hash esatti del pacchetto v0.4. Secondo boot: D3D11 hardware11_0 conservato. Nessuna prova scena/app OpenGL o installazione guest.

**Gate guest fallito, ora più preciso:** con diagnostica process-local `VN_DEBUG=init,result`, `MESA_LOG=file`, `MESA_LOG_LEVEL=debug`, l'ICD si collega al renderer e concorda wire1, XML1.4.343, protocolspec4; poi registra `failed to allocate/map ring shmem` e restituisce `VK_ERROR_OUT_OF_HOST_MEMORY`. L'errore non dimostra esaurimento della RAM fisica. La libreria Vulkan in Windows non ha ancora un buffer di comandi utilizzabile, quindi non ha senso aggiungere Zink o avviare Creality ora.

Il confronto sorgenti individua una differenza concreta: Venus Win32 conserva il percorso allocation/map/lock tradizionale; Neptune gestisce esplicitamente WDDM2/GpuMmu, identità allocazioni, submit virtuali e `RES_INFO.UserVa` per la memoria mappata dal KMD. È l'ipotesi d'intervento user-mode da verificare, non la prova che il singolo fallimento sia già attribuito a una specifica chiamata. Una sola traccia ETW Resource/Memory ha37eventi e non restituisce un NTSTATUS utile: non ripeterla o allargarla senza nuova domanda.

**Prossimo passo minimo:** diagnosticare/adattare il percorso memoria della sola libreria Vulkan user-mode all'interfaccia WDDM2 del KMD firmato. Verifica iniziale: ring creato/mappato e prima GPU Vulkan enumerata nel clone; soltanto dopo buffer GPU/lettura reale e scena Zink. Non modificare il kernel o i file firmati installati per tentativi. La candidata host rimane privata e non promossa: va qualificata con gli stessi controlli e il percorso applicativo completo prima della distribuzione.

**Operatività e fallimenti:** il primo boot manuale ometteva `PERP_NEPTUNE_CONTEXT_RETIREMENT=1`, già richiesto dall'app ordinaria; ritiro non confermato e ammissione chiusa. È un errore della preparazione del clone, corretto conservando il gate, non un nuovo difetto del driver. Build iniziale non trova il link libepoxy rimosso dalla vecchia directory; collegata la copia privata della libreria corrente, usando gli argomenti Objective-C effettivi del linker. Tentativi iniziali QEMU privato richiedono dipendenze Runtime e variabili del broker nativo: risolti prima del boot Windows.

Entrambi i tentativi di arresto ordinario del clone non fanno uscire QEMU; arrestato esclusivamente il runtime sacrificabile con QMP dopo controllo del suo UUID, preservando gli overlay dei fallimenti. Listener diagnostico fermato, nessun trace ETW lasciato attivo. Nessun arresto/riavvio impartito alla main. Il controllo conclusivo trova però un nuovo PID main76030 rispetto a74247: causa non isolata, non dichiarata conservazione della sessione. La configurazione main è byte-identica; graphics_info torna D3D11 hardware11_0. Diario per l'ultimo stato del frontend e i limiti.
